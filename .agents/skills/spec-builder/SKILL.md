# Spec Builder

让用户通过自然对话产出一份**逐步生长的**软件需求说明书。核心不是"聊完后甩出文档"，而是每轮对话都让 `spec.md` 长出新内容，用户随时能看到当前进度和缺口。

## 工作流（每轮对话固定 4 步）

### Step 1 — 加载状态

在工作区根目录查找 `spec.md` 和 `spec.meta.json`：

- **首次启动**：把 `assets/spec.md` 和 `assets/spec.meta.json` 复制到工作区，然后立即询问用户两件事——"这个软件给谁用？""它要解决什么核心问题？"这两个问题不锁住，后面所有章节都会跑偏。
- **后续轮次**：读取现有文件，了解当前进度。

### Step 2 — 抽取断言

从用户最新输入中识别可落档的"断言"。每条断言必须能映射到 `spec.md` 的某个章节。例：

| 用户原话                      | 抽取断言                             | 落到   |
| ----------------------------- | ------------------------------------ | ------ |
| "给销售用的报价工具"          | 目标用户 = 销售；项目类型 = 报价工具 | §1, §3 |
| "客户能看到报价单状态"        | 用户故事：客户 - 查看报价状态        | §4     |
| "不做支付，对接现有 ERP 就行" | 非目标：支付；技术约束：集成 ERP     | §3, §7 |
| "PDF 导出 3 秒以内出来"       | 性能：导出 ≤ 3s                      | §6     |

**如果一句话同时落 2 个以上章节，是正常的**——按章节分别记。

每条断言用稳定编号：功能 `F-001`、用户故事 `U-001`、非功能 `N-001`、约束 `C-001`、开放问题 `Q-001`。编号一旦给出不复用、不重排，方便用户引用"刚才那条 F-003 改一下"。

### Step 3 — 写入文件

用 `Edit` 工具把断言落到 `spec.md` 对应章节。规则：

- **追加而不是覆盖**：在章节末尾插入新条目。
- **同步更新 `spec.meta.json`**：把对应章节状态从 `empty` → `draft`。
- **用户明确确认后才升级为 `confirmed`**（例如用户说"对，就这样"、"OK"、"没问题"）。
- **保留原始用词**：用户说"销售"就不要写成"销售人员"，需要规范化时单独加一行 `// 标准化为：xxx` 说明。

### Step 4 — 推进 + 覆盖度报告

回复用户时**先后顺序固定**：

1. **复述刚落档了什么**（1-2 句）：「我把 "PDF 导出 3 秒内" 记到了 §6 非功能需求 N-002。」
2. **覆盖度小报告**（紧凑表格或一行字）：
   ```
   覆盖度：§1✓ §2✓ §3• §4• §5○ §6• §7○ §8○
   （✓ confirmed / • draft / ○ empty / ⊘ skipped）
   ```
3. **下一个引导问题（仅在 guide 模式）**：从当前 `empty` 章节中选**最阻塞后续的那个**问一个具体问题。**一次最多问 2 个，不要列 5 条**。优先级：§1 §3 §4 > §5 §7 > §6 §2 §8。

## 两种模式

启动时默认 **guide 模式**。用户可以随时用 `/freestyle` 或 `/guide` 切换，把当前模式写进 `spec.meta.json` 的 `mode` 字段。

### guide 模式（强引导）

- 智能体主动按章节追问
- 每轮回复必须以"下一个问题"结尾
- 用户说"跳过 §6" → 把章节状态置为 `skipped`，不再追问，最终总结时提醒"以下章节被跳过"

### freestyle 模式（用户主导）

- 智能体只做 Step 1-3，**不主动追问**
- 第 4 步只输出覆盖度报告，不带问题
- 用户随时切回 guide

## 章节判定标准

详见 `references/completeness.md`。**升级到 `confirmed` 之前必查这份清单**，避免"看起来填了但其实没用"的章节。

## 常见漏洞与反模式

详见 `references/red-flags.md`。**每填完一节都过一遍这份清单**，发现问题主动追问而不是等用户发现。

## 参考范例

用户问"你能写成什么样"或写到一半卡住时，加载 `references/example-saas.md`，里面是一份填好的范例（B2B 报价工具）。但**不要把示例内容直接搬到用户的 spec.md**，只用来对齐风格和颗粒度。

## 导出

当用户说"导出"、"下载"、"生成文档"、"发给老板"时，按目标格式调用 open-cowork 内置 skill：

| 用户意图           | 调用         | 输入                                          | 输出               |
| ------------------ | ------------ | --------------------------------------------- | ------------------ |
| Word 文档          | `docx` skill | `spec.md`                                     | `spec.docx`        |
| PDF 归档           | `pdf` skill  | `spec.md`（先转 docx 再转 pdf 或直接 md→pdf） | `spec.pdf`         |
| PPT 大纲（评审用） | `pptx` skill | 把 §1 §3 §4 §5 §8 抽成大纲传过去              | `spec-review.pptx` |

PPT 不要每节一页地全搬过去——评审 PPT 只要 8-12 页，重点是 §1 概述、§3 目标/非目标、§4 关键用户故事（选 3-5 条）、§5 功能模块图、§8 里程碑。其他细节放 appendix。

## 反模式（绝对不要做）

- ❌ 一次问 5 个问题（一次最多 2 个）
- ❌ 替用户决定关键选项（给 2-3 个候选让用户选）
- ❌ 在没有落档的情况下纯聊天（每轮必须有 Edit 动作或明确说"本轮无新增"）
- ❌ 把 spec 内容写在聊天回复里而不写进文件（**文件是真相源**）
- ❌ 编号重排（编号给出后永不变动）
- ❌ 用 docx skill 之前不先确认 spec.md 已经到一定完成度（建议 ≥ 60% 章节 confirmed）

## 完成判定

满足任一条件视为可交付：

- 所有非 `skipped` 章节都为 `confirmed`
- 用户明确说"完成"、"够了"、"就这样吧"、`/spec done`

完成时输出最终报告：覆盖度、跳过的章节及原因、开放问题清单（§8 的 Q-xxx）、建议的下一步（"是否要导出 docx？"）。
